# What "cell" names

Item 5 of [`open-work.md`](open-work.md). A proposal, not a change — nothing is
renamed here. Counts and line anchors come from a sweep of the working tree on 2026-08-17
(`rg -i cell` minus `node_modules`, builds, `probes/artifacts` and other lanes'
untracked files); the per-file table is at the end.

## The word today

254 lines in 64 files. Almost all mean **one frontend app**: "the four cells",
"this cell" in every `frontends/*/README.md`, `HOSTED_CELLS`, `build_cell`,
`HOSTED.cells`. That is the sense the code encodes and the sense the jinja plan
was written in ("a server-rendered monolith cell", `frontends-jinja.md:1`).

The **square** sense — a frontend × backend pair — appears in prose once:
`README.md:8`, "the first cell was assistant-ui × pydantic-ai; there are four in
the matrix now", which slides from pair to frontend mid-sentence. The hub, the
only place a square is drawn, never calls it a cell: the visible copy says
*square* five times ("Every square runs the same agent", "N of 16 squares
live"), `renderSquare` draws one, and the readout labels its `f × b` line with a
`.pair` class. Its one `cell` local (`index.html:536`) is `el.closest("td, th")`
— an HTML table cell, headers included, which is neither sense.

Two more senses ride along. A **backend calling itself a cell** — "this cell
exists to answer…" (`backends/pi-rpc/README.md:10`), "the Cloudflare cell"
(`README.md:177,198`), "the pi cells" (`backends/pi/src/main.ts:121`), "pi-rpc
landed as its own cell" (`docs/architecture.md:217`): 12 lines, 7 files, wrong
under either option. And "the one cell outside the matrix" for jinja
(`frontends/jinja/README.md:8`, `pyproject.toml`, the uncommitted PAGES entry at
`index.html:609`), which only parses if cell ≠ square.

Nothing public-facing carries the word: worker names are `chat-stack-<dir>`,
probe artifacts are `artifacts/<backend>/<flow>/…` and
`manifest/<backend>--<flow>--<frontend>.json` with `backend` and `frontend`
fields (keyed that way since `10105b8`), and the one baked key, `HOSTED.cells` in `index/dist`,
is regenerated by `build_index` and has no live consumer — `chat-stack-index`
and the frontend workers 404 today (curl); only the backend is up.

## Option A — code says "frontend"; "cell" becomes the square

**57 files** (64 minus `shadcn/app/typeset.css`, which means HTML cells, and the
six dated `docs/plans/*` records). Nine carry identifiers or matched strings
that break or mislead if missed — `scripts/hosted.sh`, `preview.sh`,
`publish.sh`, `probe.sh`, `probes/frontends.ts`, `probes/matrix.spec.ts`,
`index/index.html`, `frontends/jinja/templates/base.html`,
`frontends/jinja/static/app.css` — about 30 tokens: `HOSTED_CELLS` (8 uses, the
regex at `frontends.ts:163` that reads it, the skip title at
`matrix.spec.ts:21`), `cell_port`/`cell_url`/`build_cell`,
`cellUrl`/`hostedCells`, the JSON key `cells` (one producer, three reads in the
hub), `data-cell`/`.cell-name` (nothing else reads them). The other 48 are prose
and comments where the meaning *flips*, so every line is re-read rather than
replaced: `README.md` 26, `probes/README.md` 17, `docs/architecture.md` 10,
seven READMEs, ~30 one-line comments and metadata strings. The 12 backend-sense
lines become "backend".

It buys internal consistency: `FRONTENDS` beside `HOSTED_FRONTENDS`,
`frontendUrl` reading `HOSTED.frontends`. What stays ambiguous: the square gets
a third name (cell, square, `.pair`) unless the hub copy is swept too (~15
lines), and the meta description on every frontend page — "One cell of the
chat-stack comparison matrix" — changes meaning underfoot (still true: a page
opened with `?backend=` is one square). Eight of the 57 files hold other
sessions' uncommitted hunks today, so the sweep waits on them or splits diffs.

## Option B — "cell" stays a frontend; the square is a "pair"

**2 to 8 files**, no identifier moves. `README.md:8` becomes "the first pair
was…"; the definition is written once at first use (`README.md` "What's here",
`docs/architecture.md`): *a cell is one frontend; a pair is a frontend against a
backend; the hub draws a pair as a square*. That is what the hub already does,
so B mostly writes down what it draws. Optionally the hub's `cell` local becomes
`td` (two lines).

The sub-question is whether "cell" covers backends. Wide — "one stack, either
axis" — matches every line but `README.md:8` and stops at two files, but with
four backends live it makes "the four cells" ambiguous. Narrow costs the 12
backend-sense lines in 7 files and is cleaner.

What stays ambiguous: a reader arriving table-first expects cell = square until
the README's first sentence corrects them, and `HOSTED_CELLS` keeps sitting next
to `FRONTENDS` meaning "the hosted subset of it". If that grates, A's nine-file,
~30-token identifier rename can ride along without the prose flip — the only
part of B that would touch a key (`HOSTED.cells`, unpublished) or a test title.

## Recommendation

**B, narrow.** Usage runs ~170 lines to 1; the code already says "frontend" for
the axis everywhere but the hosted subset; and the hub has already named the
square without "cell", so A spends a 57-file meaning flip to free a word nothing
then needs. B's real cost is that "cell" stays a term of art the README must
define in its first paragraph — cheap, and the hub visitor never meets the word.
Eight files at most, no identifiers, no public key.
