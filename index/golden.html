the golden check

The comparison only means anything if every backend hands a frontend the same work. protocol/conformance.sh checks that the events a frontend depends on exist; this is the check that goes one step further and asks whether the backends actually agree.

Why it exists

Every backend keeps its own copy of the scripted model and its three tools — backends/pydantic-ai is the reference, and cloudflare-agents, pi and pi-rpc each reimplement it in a different framework. Nothing enforced that the copies stayed in sync except a person, once, diffing captured streams by hand after normalising the ids — which is how a real drift got found and then only written down in a README instead of fixed. The golden check replaces that hand diff: it runs the same comparison as a matter of course, and prints the drift instead of describing it.

What it checks

For each backend, five prompts against both wire protocols — /chat (the Vercel AI data stream, SDK v7) and /ag-ui — ten streams in all. Each one is reduced to a canonical form and diffed against a fixture captured from the reference, backends/pydantic-ai at :8001.

flowprompt
weatherWhat's the weather in Tokyo?
notesSearch notes for streaming protocols.
analyzeAnalyze assistant-ui as a chat frontend.
follow-upweather, then notes, on one thread — the fixture is turn two
multi-toolWhat's the weather in Tokyo, and search notes for streaming?

The canonical form erases exactly what's allowed to differ between two correct implementations, and nothing else:

  • id values (id, toolCallId, messageId, parentMessageId, threadId, runId) at a frame's top level, renamed by first appearance — so pairing is checked and the values themselves aren't
  • timestamps at a frame's top level
  • pydantic-ai's message-metadata timestamp stamp — that exact frame, nothing broader

Everything else is compared as it streams:

  • event order and delta boundaries — a backend that stops streaming and sends one burst instead gives a frontend different work
  • tool names, argument JSON, and tool results
  • finish state

Recorded run

Exceptions

A backend that drifts either gets fixed, or gets an exception — per backend, per field, with a reason, in protocol/golden/exceptions.json. Every exception applied is printed on the run rather than silently passed. One today:

cloudflare-agents · /chat · finish.finishReason

The AI SDK stamps finishReason on the finish chunk unconditionally — there's no way to send the chunk without it — where the reference's adapter sends none. No cell reads the field; stripping it would mean post-processing the SDK's own stream to remove information rather than fixing a difference in behaviour.

Run it

# every backend in scripts/stacks.sh, needs scripts/run.sh already up
./scripts/golden.sh
# or: mise run golden

# one backend
bun protocol/golden.ts http://localhost:8002

# recapture the fixtures from the reference, after a deliberate change to it
bun protocol/golden.ts --update

It refuses to run against anything but the scripted model — golden compares bytes, and a real provider writes different bytes every time, so there'd be nothing in the diff to learn from.

What it doesn't catch

Timing and pacing — pi-rpc's tool arguments arrive in a burst at toolcall_end rather than streaming, because pi's RPC wire drops partials until the call id is known; same bytes, different pacing. HTTP headers. Rehydration (GET /threads/{id}), which diverges by construction — pydantic-ai and cloudflare-agents are client-authoritative, the two pi backends are session-authoritative, and protocol/CONTRACT.md documents both. Whether a backend actually reads the history it's sent, as opposed to merely accepting it. Id values — pairing is checked, not the value itself. Anything a real (DEMO_MODEL) model does; the check only means something under the scripted one.
